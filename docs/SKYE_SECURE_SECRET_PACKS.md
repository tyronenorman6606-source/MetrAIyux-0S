# SkyeSecure Secret Packs

SkyeSecure Secret Packs is the encrypted developer handoff lane for files that normal Git and safe vault archives must ignore: `.env` files, private keys, credential JSON, local recovery tokens, database dumps, and other client-owned operating material.

This is not a password zip. The `.skyesecrets` format encrypts the payload locally, stores only ciphertext in SkyeVault/Drive, and restores plaintext only after an approved recipient unlocks the pack.

Implemented in this repo:

- `packages/skye-secure/skye-secure-core.mjs`: SKYESEC2 crypto, envelope validation, payload validation, key wrapping, restore logic.

- `metraiyux_0s_site/skye-secure-secret-packs/app.html`: standalone local packer and passphrase unlocker.

- `tools/skye-secure-audit-bundle.mjs`: audit packet generator with source hashes, proof hashes, syntax checks, and npm external advisory audit.
- `tools/skyevault-repo-push.mjs`: vault upload now accepts encrypted pack MIME/type metadata.
- `tools/skye-secure-platform.mjs`: vault-aware platform CLI for inventory, search, offload, reload, access policy, and audit logs.
- `metraiyux_0s_site/skye-secure-platform/index.html`: browser console for safe vault index, policy, and audit review.

Not claimed:

- Revocation only affects newly written pack copies. Anyone with an older pack copy and a valid old key can still decrypt that older copy.

## Format

Serialized packs start with:

```text
SKYESEC2\0
```

The JSON envelope contains:

- `publicManifest`: safe metadata, pack ID, workspace/repo labels, file count, byte counts, algorithm labels, and source-boundary hash.
- `encryptedPayload`: AES-256-GCM ciphertext of the internal restore payload.
- `wrappedKeys`: one or more encrypted content-key wrappers.
- `integrity`: SHA-256 checks for the public manifest and encrypted payload.

The encrypted payload contains:

- file paths
- file modes
- file sizes
- per-file SHA-256 hashes
- base64 file bytes
- restore policy
- optional source-boundary report

## Cryptography

- Payload encryption: `AES-256-GCM` with a random 32-byte content key and 12-byte IV.
- Passphrase wrapping: `PBKDF2-SHA256`, default `310000` iterations, 32-byte random salt, optional pepper, then `AES-256-GCM` content-key wrap.
- Public-key wrapping: `X25519` ephemeral ECDH, `HKDF-SHA256`, then `AES-256-GCM` content-key wrap.
- Integrity: SHA-256 over canonical public manifest JSON and encrypted payload bytes.

Hashing is used for proof and tamper detection. Encryption is used for anything that must be opened again.

## Operator Workflow

Generate the local-only path checklist:

```bash
npm run vault:secrets:manifest
```

Pack reviewed paths with a passphrase recipient:

```bash
SKYE_SECURE_PASSPHRASE='long client passphrase' \
SKYE_SECURE_PEPPER='separate high-entropy pepper' \
npm run skye-secure -- pack \
  --root=. \
  --paths-file=.skyevault-out/secret-boundary/secret-boundary-YYYYMMDDTHHMMSSZ.paths.txt \
  --out=.skyevault-out/skye-secure/client.skyesecrets \
  --recipient=owner \
  --passphrase-env=SKYE_SECURE_PASSPHRASE \
  --pepper-env=SKYE_SECURE_PEPPER \
  --workspace=client-workspace \
  --repo=MetrAIyux-0S
```

Inspect public metadata without decrypting:

```bash
npm run skye-secure -- inspect --pack=.skyevault-out/skye-secure/client.skyesecrets
```

Verify and decrypt without restoring:

```bash
SKYE_SECURE_PASSPHRASE='long client passphrase' \
SKYE_SECURE_PEPPER='separate high-entropy pepper' \
npm run skye-secure -- verify \
  --pack=.skyevault-out/skye-secure/client.skyesecrets \
  --recipient=owner \
  --passphrase-env=SKYE_SECURE_PASSPHRASE \
  --pepper-env=SKYE_SECURE_PEPPER
```

Restore into a workspace:

```bash
SKYE_SECURE_PASSPHRASE='long client passphrase' \
SKYE_SECURE_PEPPER='separate high-entropy pepper' \
npm run skye-secure -- restore \
  --pack=.skyevault-out/skye-secure/client.skyesecrets \
  --root=/path/to/workspace \
  --recipient=owner \
  --passphrase-env=SKYE_SECURE_PASSPHRASE \
  --pepper-env=SKYE_SECURE_PEPPER
```

Create a public-key recipient:

```bash
npm run skye-secure -- keygen --recipient=developer-name --out-dir=.skyevault-out/skye-secure/keys
```

Grant a developer key to a new copy:

```bash
SKYE_SECURE_PASSPHRASE='long client passphrase' \
SKYE_SECURE_PEPPER='separate high-entropy pepper' \
npm run skye-secure -- grant \
  --pack=.skyevault-out/skye-secure/client.skyesecrets \
  --out=.skyevault-out/skye-secure/client-granted.skyesecrets \
  --recipient=owner \
  --passphrase-env=SKYE_SECURE_PASSPHRASE \
  --pepper-env=SKYE_SECURE_PEPPER \
  --recipient-key=developer-name:.skyevault-out/skye-secure/keys/developer-name.public.json
```

Upload ciphertext to SkyeVault:

```bash
npm run skye-secure -- upload --pack=.skyevault-out/skye-secure/client.skyesecrets
```

## Browser Unlocker

Open:

```text
metraiyux_0s_site/skye-secure-secret-packs/app.html
```

The browser app:

- creates `.skyesecrets` packs from selected local files
- reads `.skyesecrets` files locally
- validates public envelope integrity
- decrypts passphrase-wrapped content keys with WebCrypto
- decrypts the payload locally
- verifies each file hash and size
- creates per-file downloads
- exports a local unlock receipt without secret values

## Client Trust Rules

- Never put `.skyesecrets` passphrases or peppers in Git.
- Store passphrases and peppers in separate custody paths.
- Upload only `.skyesecrets` ciphertext to SkyeVault/Drive.
- Treat public manifests as safe metadata, not proof of authorization by themselves.
- Rotate packs when a developer leaves or a passphrase may be exposed.
- Use `--dry-run` before restoring into a workspace with existing files.
- Keep local receipts private if path names are sensitive.

## Next Major Lane: Vault Offload And Reload

The platform layer now handles removable project material such as `/workspaces/MetrAIyux-0S/about to delete`:

- scan a folder before deletion
- classify files, types, sizes, routes, imports, references, and risk
- encrypt and offload the folder into SkyeVault/Drive
- keep an index of what is in the vault
- support bash/CLI queries like inventory, type filters, search, proof, download, and reload
- restore the folder back into the project on demand
- prove that deleting the local folder does not break active routes/tests before removal

The current implementation covers encrypted offload, inventory, type search, access policy, audit logs, and reload proof. Deletion itself should remain a separately approved action after dependency and route checks are green.
